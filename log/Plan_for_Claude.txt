# DMAIC: TTS Audio Not Playing — Detailed Investigation & Fix Plan

## Context
Speech worked in earlier sessions but now produces no audio at all. AllTalk and Whisper
services are healthy. The MCP server logs show streaming TTS initiates (header parsed,
24000Hz/1ch/16bit detected) but then the MCP framework logs "Request 2 cancelled -
duplicate response suppressed" — an anyio.CancelledError caught at
mcp/server/lowlevel/server.py:766. There is a critical logging gap between streaming
start and completion — we cannot see whether audio bytes are actually being written or
played.

### Cancellation Source
Found in: venv\Lib\site-packages\mcp\server\lowlevel\server.py lines 766-771
```python
except anyio.get_cancelled_exc_class():
    logger.info("Request %s cancelled - duplicate response suppressed", message.request_id)
    return
```
This fires when the async handler running await handler(req) is cancelled by anyio.
The handler wraps: await asyncio.to_thread(speak_text, text, voice)

### Critical Logging Gap
Between "Streaming TTS: 24000Hz, 1ch, 16bit" and "Request 2 cancelled" there is
ZERO logging of:
- Whether sd.RawOutputStream actually started
- Whether any audio chunks were written
- How many bytes total were written
- Whether the chunk-writing for loop executed at all
- Whether any exception occurred during writing
- Whether the finally block (drain/stop/close) executed
- Whether stream.active was True or False at any point

We MUST NOT guess the root cause. We must add logging first.

## DMAIC PHASE 3: GENERATE SOLUTIONS (conditional on diagnostic output)

### Scenario A: Chunks are written but no audio plays
Root cause: sounddevice output device issue
Evidence: Log shows "First chunk written" and "Streaming loop done: N chunks, M bytes"
         but user hears nothing
Fix: Add explicit device parameter to sd.RawOutputStream, or add blocksize/latency
     params. Verify with sd.query_devices() logged at startup.

### Scenario B: No chunks written (loop never executes or exits immediately)
Root cause: response.iter_content() blocks or returns empty
Evidence: Log shows "Stream started" but no "First chunk written"
Fix: Debug AllTalk streaming response. Add per-chunk timeout. Verify iter_content
     yields data by logging chunk sizes.

### Scenario C: Exception during chunk writing
Root cause: sounddevice write error (buffer, device, format)
Evidence: Log shows "Chunk writing error: ..."
Fix: Address specific error. May need blocksize, latency, or device params.

### Scenario D: Thread killed by async cancellation before playback
Root cause: asyncio.to_thread + anyio cancellation kills the thread or prevents writes
Evidence: Log shows "Stream started" but nothing after — no chunks, no finally block
Fix: Decouple audio playback from async response lifecycle. Run the actual streaming
     playback in a fire-and-forget daemon thread using threading.Thread(daemon=True).
     The MCP handler starts the thread and returns immediately. Audio continues
     independently of MCP request lifecycle.

     Implementation:
     - speak_text_streaming() stays as-is (the actual streaming logic)
     - In call_tool(), instead of await asyncio.to_thread(speak_text, ...),
       start speak_text in a daemon thread and return the result dict immediately
     - The daemon thread handles all audio playback independently
     - MCP cancellation can no longer affect audio output

### Scenario E: Stream starts and writes but finally block kills audio prematurely
Root cause: The while stream.active loop exits too early, or stream.stop() is called
            before audio finishes playing
Evidence: Log shows chunks written, but "Draining stream, active=False" immediately
Fix: Add a small sleep after writing last chunk before checking stream.active,
     or use stream.write() with blocking mode to ensure all data is played.
